## Open-issue analysis

### #46 K1C 2025: no camera feed

- **Report.** K1C 2025 hardware (DWIN hw `CR4SU200382C13`, sw `V1.0.0.22.20250711S`) reports `model: K1C` and `webrtcSupport: 1`. Its camera is WebRTC on `:8000/call/webrtc_local` (base64 JSON SDP), not MJPEG on `:8080`. The integration onboarded it as MJPEG and the camera never loaded. Later commenters with K1C / K1 Max on firmware 1.3.5.22 saw the same after a firmware update; forcing "WebRTC (go2rtc)" fixed theirs (2026-08-29, 2026-09-30). For the original K1C 2025 hardware, go2rtc completes the handshake but never receives a frame (log of 2026-09-09). A commenter traced that with packet captures (2026-01-05): the printer's SDP answer lists payload types 0 and 96 but it sends 98.
- **Status on 0.9.9.** No fix. The maintainer said on 2026-10-02 that detection will be rewritten to fall through to the next working camera mode.
- **Root cause in code.**
  1. Camera type is computed once and cached forever: `__init__.py:351-359` only sets `_cached_camera_type` when it is missing, so a firmware update that moves a printer from MJPEG to WebRTC is never noticed.
  2. Two detection paths disagree. Onboarding uses `is_k2_family or supports_webrtc` (`__init__.py:353`). The options flow's "Auto" maps every K1-family printer and the Creality Hi to MJPEG before it probes anything (`config_flow.py:320-334`), ignores `webrtcSupport`, and stores the resolved mode instead of "auto" (`config_flow.py:387-391`). Re-saving camera options with Auto therefore pins a WebRTC K1C to MJPEG.
  3. The K1C 2025 media failure sits in go2rtc/pion or the printer firmware. The direct mode (`camera.py:1059-1203`) rebuilds m-line order but does not touch payload types, so it most likely hits the same mismatch in the browser. Not verified.
  4. The "source mismatch ... Recreating" warnings in the 2026-09-09 log are churn on top (see #88), not the cause.
  5. The README contradicts itself: `README.md:738` says the K1C 2025 is auto-detected as WebRTC, while `README.md:798` says its camera is not supported.
- **To close.** Split the issue. (a) Detection: one detection function for both paths, trust `webrtcSupport`, re-detect when `modelVersion` changes, and fall back at runtime (configured mode, then MJPEG probe, then go2rtc WebRTC, then direct) after repeated stream failures. (b) K1C 2025 media: get a reporter to capture one offer/answer pair; if the payload-type mismatch is confirmed, test a payload-type rewrite in direct mode, otherwise document it as blocked upstream.
- **Policy.** No conflict: the camera and its endpoint are real.

### #121 Some entities stay unavailable after power-on (closed 2026-10-02)

- **What was fixed.** `number.<printer>_chamber_target` was created only if `maxBoxTemp` had arrived before platform setup, so an HA restart while the printer was off left it uncreated until the next reload. It now uses the cached capability and late discovery (`number.py:43-77`, `coordinator.py:569-594`; `test_late_discovery.py`). That matches "regularly but not always" and "reload fixes it".
- **What was not.** The attached log shows `ValueError: Sensor sensor.<printer>_bed_temperature ... non-numeric value: ''` for bed and nozzle at power-on. `KSimpleFieldSensor.native_value` returns the raw telemetry value (`sensor.py:288`), so a booting printer that sends `''` still fails the state write, and the entity keeps its previous state, which after a power-off is `unavailable`. Hypothesis, not verified: if the printer only re-sends a field when it changes, a slowly moving `boxTemp` can stay `''` in the merged data for a long time, which would explain "most of the time it is exactly the chamber temperature that is stuck". A boot capture would settle it.
- **To close properly.** Return `None` for non-numeric values in numeric sensors, add a test that replays a power-on sequence with empty strings, and ask the reporter to confirm on 0.9.8. Cite #121 in the CHANGELOG.

### #122 Expected filament length/weight from G-code metadata (open)

### #124 "Stopped at 0%" while self-testing (open)

- **Status.** Fixed on 0.9.9 by `df19ff3`: `JobEndWatch.observe` treats `self-testing` as neither running nor stopped and clears any pending stop timer (`notification_rules.py:634-641`). Pinned by `test_notification_rules.py::test_a_self_test_after_the_first_printing_frame_is_not_a_stop` and `test_notification_live.py::test_a_self_test_at_the_start_of_a_print_is_not_a_stopped_print`. CHANGELOG 0.9.9 cites it.
- **Root cause.** `RUNNING_JOB_STATES` (`notification_rules.py:533`) is narrower than `BUSY_PRINT_STATES` (`utils.py:486`), so after one `printing` frame the self-test was treated as an ambiguous stop and confirmed after `NOTIFY_END_CONFIRM_SECS`.
- **To close.** Release 0.9.9. A print cancelled during the self-test is only announced after the self-test ends; that is a documented trade-off.
- **Policy.** No conflict.

### #125 iOS live print card never appears (open)

- **Finding 1, confirmed.** `_async_deliver_one` runs `stringify_data` on every companion-app target (`coordinator.py:2240-2244`), even though `_target_os()` (`coordinator.py:2050`) already knows the OS. iOS therefore gets `live_update`, `progress`, `progress_max`, `chronometer`, `when` and `alert_once` as strings. The reporter showed that the same payload with native types creates the Live Activity and with strings does not. `test_notification_wire_format.py::test_no_native_scalar_survives_a_realistic_live_payload` (line 88) applies the Android rule to every target, so it pins the iOS bug.
- **Finding 2, unexplained.** Even with native types, the integration's own start push produced no card, while re-sending the logged payload by hand did. Only the first push carries `activity: start` (`notification_rules.py:1018-1021`), so a lost start is never recovered. Needs a companion-app side capture.
- **Finding 3, confirmed.** A stale `err` (500 / key 116) makes the status sensor read `error` for the whole print. That is by design (`utils.py:517-520`; activity state is used for control, `coordinator.py:445-466`). But a new file name resets `_last_error_code` and `_notified_filament_runout` (`coordinator.py:950-954`), so the same stale error (`:1049-1060`) and a stale runout (`:1070-1081`) notify again at every print start. `test_notifications.py::test_stale_error_at_startup_does_not_notify` covers HA restart only, not a file change.
- **Push volume.** `NOTIFY_LIVE_MILESTONE_STEP = 1` with a 30 s floor (`const.py:239,253`) allows about 100 pushes per print against the relay's 500 per day.
- **To close.** A per-OS serializer (strings for Android, native types for iOS) with wire tests per OS; keep the error and runout latches across a file change while the code is unchanged; repeat `activity: start` until a card is likely to exist, or at least on the first milestone. Ask the reporter for a companion-app log for Finding 2.
- **Policy.** No conflict.

## Process observations

- **Response time.** Reporter issues opened from October 2025 to January 2026 got a first maintainer reply in a median of 5.3 hours (30 issues). From February 2026 the median was about 21 days (11 issues), and 8 reporter issues got no maintainer comment at all (#67, #87, #102, #103, #106, #116, #124, #125). Five of those (#87, #102, #103, #106, #116) were fixed by a merged PR with no word on the issue.
- **Traceability.** Only 12 of 64 closed issues link to a commit or PR: #50, #52, #69, #87, #88, #101, #103, #106 and #115 through issue events, and #8, #102, #116 through PR bodies. The rest were closed with "released in X" or "added to 0.6.6". Commit messages rarely cite issues: only 8 issues appear in any non-merge commit message (#52, #87, #88, #101, #103, #106, #115, #124); the 0.9.8 fixes for #112, #113, #116 and #117 are cited in code comments and the CHANGELOG but not in commits.
- **Closed without confirmation.** #72, #77, #80 and #84 were closed with "released in 0.9.3, closing"; #103, #106 and #116 by the release with no comment; #113, #117 and #121 on 2026-10-02, five days after "fix released in 0.9.8". #121 is only partly fixed.
- **State reasons.** Only #93 uses "not planned". #24 (won't fix), #33 (not possible), #34 (stale), #47 (not a bug), #67 (duplicate) and #76 (not reproducible) are all "completed".
- **Labels.** 12 issues have no labels (#3, #8, #11, #18, #48, #58, #59, #67, #69, #87, #101, #102). `done` is on 23 issues but missing from fixed ones such as #102, #103, #106 and #116. Type labels are sometimes wrong: #114 is labelled bug but needed only documentation, #33 is titled "[Bug]" and labelled feature request.
- **Milestones.** Milestones exist only for v0.6.5, v0.7.0, v0.8.0, v0.9.8 and v0.9.9; v0.8.0 and v0.9.8 are still open after release. The CHANGELOG links every release from 0.7.0 to 0.9.8 to a milestone query, but 0.7.1 and 0.9.0 to 0.9.7 have no milestone, so those links return empty lists. The links at `CHANGELOG.md:295,303,319,344,366,375` are also missing their closing parenthesis.
- **CHANGELOG coverage.** There are no entries before 0.7.0, so #3 to #31 era fixes are undocumented. Entries from 0.7.0 to 0.9.2 never cite issue numbers (#35 to #40, #43 to #45, #49 to #53, #58, #59, #65, #66 and #69 are fixed but uncited). #45 sits under 0.7.1's "Minor bug fixes". #71 is cited only through PR #73. #121's fix is described in 0.9.8 without its number, so `release_references.yml` would not have commented on it. Citations have been reliable since 0.9.3.
- **Template compliance.** Markdown templates arrived on 2025-11-14 (`090ec4a`). The issue forms and the validator exist only on branch `0.9.9` (`da0295a`); `main` still serves the markdown templates and has none of the issue workflows. Of the reporter issues opened since the templates appeared, 7 skipped them (#34, #40, #67, #69, #77, #87, #102), and at least 8 bug reports left "I included diagnostic output" unticked (#53, #65, #71, #72, #88, #99, #103, #113). The maintainer had to ask for the template or logs in #34, #46, #51 and #88.
- **Auto-close workflows, replayed against history.**
  - `issue_validator.yml` (templateless gate) would have closed #67, #69, #77, #87 and #102 as not planned. #87 was the exact root-cause report behind the 0.9.4 hotfix, #69 led to PR #70, #102 to PR #108, #77 to a 0.9.3 fix. #87 is missed because its headings are indented by one or two spaces; the regex requires `#` in column 0, while GitHub renders up to three leading spaces as a heading.
  - `close_done_issues.yml` would have closed #4 at 2025-11-06 10:00 Prague: it carried `done` and the owner had commented last on 2025-10-31, but the working release (v0.6.3.5) came out later that day and the reporter confirmed on 2025-11-07. On its first run on `main` it will close #122, which the maintainer asked to keep open. Because `done` goes on at merge time, any owner comment on a merged-but-unreleased fix starts a five-day clock that can close the issue before the release exists.
  - `close_incomplete_issues.yml` needs the validator's bot comment, which no past issue has, so it closes nothing retroactively. #46 has carried `more info required` since 2025-12-26 with no flag, so the label is stale but harmless.
  - `validate_pr.yml` requires an `accepted` linked issue. Most merged external PRs (#5, #9, #57, #61, #70, #73, #81, #91, #107, #108) had none and would have been closed under the new gate.
